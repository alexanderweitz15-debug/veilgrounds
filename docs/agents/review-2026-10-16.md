## Findings (A1 to answer in docs/agents/a1-reflex.md or the next plan-api "Changes" entry)

1. **Reflex snapshot and the fog tests.** §1 builds a snapshot per bot per tick. (a) It must go through the
   runner's `onPerceive` hook (or a second hook the fog test can subscribe to), otherwise
   `tests/bots.test.ts "snapshots handed to brains contain no hidden enemy champions"` never sees the reflex
   path and is vacuous for it. (b) Report `snapshotCostMs` separately from `reflexCostMs`: 10 snapshots at 30 Hz
   is the real performance risk, and the 0.05 ms target in §3 is for reflex, not for `buildSnapshot`. If the
   snapshot is too expensive per tick, say so and propose a cheaper per-tick view (e.g. reuse the think snapshot
   plus per-tick entity deltas) before building on it. (c) Event buffering: if reflex consumes `tickEvents`, the
   per-bot event buffer that think reads (`b.events`) must still contain every event since the last decision.

2. **Delay queue kept for non-lane nodes** (§3 says "replaced by plans"). Acceptable: reaction delays of trade,
   dodge and kite commands are not plans. Record it as a deviation in DECISIONS with the rule that no lane
   command uses `delay`/tag `'lh'` any more (gate grep), and that `busyUntil` still drops delayed move/attack.

3. **Only the next last-hit plan exists; the scheduler must still respect the window after it.** §4.1 rule 2
   requires that a filler auto does not push a minion into [0, own auto damage] of a *later* window, and that
   `freeUntil` is computed against the nearest window. With one lastHit plan the scheduler knows one window;
   when two windows overlap or follow within one attack period, the filler decision needs the predicted windows
   of the next 2-3 minions, not only `plans[0]`. State in the scheduler doc where those predictions come from
   (the per-tick planner has them) and add that to test case 3 (window collision).

4. **Parameters as data (LEAD).** The seven §4.7 fields are proposed as additive profile JSON fields (A3 owns
   the files) with code defaults in `reflexParams` "until A3 merges". §5 says no value in code. Recommendation:
   approve the shared change now and let A1 add the seven fields to all ten profile JSONs and to
   `src/ai/profiles/schema.ts` in the Phase 1 branch itself (mechanical, additive, A3 informed via
   shared-changes.md), so the Phase 1 gate has no code-side defaults at all. `schema.ts` is not in any file
   area in §12 / AGENTS-PLAN §7, so it is a shared file: approval by S, which this review gives for the
   additive fields.

5. **Log volume and fog convention for reflex entries.** Per-tick cancels with a plan id in `inputs` defeat the
   150-tick dedup (`LOG_DEDUP_TICKS` dedups identical entries only). Estimate entries per bot per minute and keep
   the 25-min game well under the 100k-entry / 50 MB cap (e.g. one entry per plan lifecycle, not per
   validation). Any x/y in reflex `inputs` (stand point, target position) must use the `<key>X/<key>Y/<key>Src`
   convention (`self` / `seen` + slot / `static`) and the node name `reflex` has to be added to
   `L_NODES` in tests/botPerception.test.ts, or the fog checker ignores it (S can do that as a supervisor fix).

6. **Overlay plumbing crosses A1/A3 (LEAD).** `reflexDebug` lives in A1's area, but the rows reach the F9 overlay
   through `debugRows` in `src/ai/log.ts` (A3) and `src/ui/botDebug.ts` (A3), called from `BotRunner.debugRows`
   (A1). Agree now: A1 extends `BotDebugRow` consumption in runner.ts and exposes `reflexDebug`; A3 extends the
   row type in log.ts and the rendering; the field names (`intent`, `plans[]{kind,targetId,inTicks}`, `util30s`,
   `stand`) are fixed by plan-api.md §5. Add the `BotDebugRow` extension to shared-changes.md.

Minor:

  is not a precondition but a scheduler rule.
